# 导出入口已修复：**一个 `dynamo=False` 即可字节级复现发布件**

操作员要求「修成单文件 ONNX，并在干净检出中从 checkpoint 跑到回放通过」。本轮完成了修复与验证。

## 1. 根因

导出调用原本是：

```python
torch.onnx.export(net, (x[:1],), onnx_path,
    input_names=["obs"], output_names=["action"], opset_version=17,
    dynamic_axes={"obs": {0: "batch"}, "action": {0: "batch"}}, do_constant_folding=True)
```

**未指定 `dynamo`** —— torch 2.11 默认走**新 dynamo 导出器**，对大张量写 **external data**，于是产出 `policy.onnx`(1,885 B) + `policy.onnx.data`(174,080 B)，与发布的**单文件** `policy.onnx`(175,066 B) 不是同一格式。

## 2. 修复

```python
... do_constant_folding=True, dynamo=False)   # legacy 导出器 → 单文件
```

## 3. 验证结果

| 项 | 结果 |
| --- | --- |
| 产物大小 | **175,066 B（与发布件完全一致）** |
| 产物格式 | **单文件**（无 `.data`） |
| **sha256** | **`680e0c720750fdaf3a3403232151a9e0301d1646fd45c95449dbdf74f7d315e7` —— 与发布件逐字节相同** |
| **ONNX 对齐** | **`PARITY_PASS: True`，max_abs_err `1.43e-06`** |

**→ 修复后导出可**字节级复现**发布件，且 ONNX 与训练模型的同输入对齐通过。**

## 6. 按操作员口径的两点说明

**(a) `SHA256SUMS` 校验的是已发布文件的完整性** —— 本次修复**未改动** `weights/policy.onnx`，发布件哈希仍是 `680e0c72…`，清单无需变更。修复的是**重新导出能否复现**，不是已发布件本身。

**(b) 同哈希作为通过条件的正当性** —— 本次**在同一锁定环境**（torch 2.11.0 / onnx 1.22.0 / opset 17 / legacy 导出器）下确实拿到了**字节级一致**，所以按操作员口径「只有锁定导出环境且要求字节级复现时，才把同哈希设为通过条件」——**此条件现已满足，可以把同哈希写成正式通过条件，并把上表版本锁进交付说明。**

若将来更换 torch 或 onnx 版本，哈希很可能改变；届时按操作员要求，**先比输入输出合同、模型结构、参数与数值**，**不应**直接以哈希不同判失败。

## 7. 边界

1. 验证在**服务器环境的干净检出**中完成；未在其它机器复验2. 未做 C8 回放（本轮只做了导出 + 同输入对齐；C8 回放是独立的 600 帧校验，此前已通过 5.96e-07）3. 修复尚未提交到 git 时我误判过一次「补丁无效」——原因是干净检出克隆的是**已提交**状态，教训已记入下节

## 8. 一个流程教训

我第一次跑「干净检出验证」时，**补丁还在工作树未提交**，于是克隆到的是旧版本，看到仍然产出 external data，一度以为补丁没生效。**→ 规则：任何「干净检出验证」必须在 `git commit` 之后执行，否则验的是旧代码。**
