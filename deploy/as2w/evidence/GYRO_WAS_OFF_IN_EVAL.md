# 🔴 重大缺陷修复：**我此前所有 Isaac 评测都是「gyro-1 关闭」的基线结果**

> **复核更正**。caps 是累计的软件限幅计数，PhysX 实际施力未测。左转近零无法据此归因于超调。见 [armD 验收复核](ARM_D_ACCEPTANCE_AUDIT.md)。

## 1. 缺陷

`tau_max` 与 `ff_max` 在**每一个用例**上都读 0。根因不是遥测坏了，而是**整条陀螺补偿路径根本没有执行**：

```python
C = st["ff"]                      # = --ff-gain
if C <= 0.0 and st["yaw_kp"] <= 0.0:   # <-- 我每次都命中这一条
    ...set_joint_velocity_target_index(target=tgt)   # 原样下发，不算 tau、不算 ff
    return
```

`st["yaw_kp"]` 来自 **`--yaw-kp` 参数**，默认 **0.0**；而我一直只设环境变量 **`AS2W_GYRO_KP=60`**，**该脚本从不读这个环境变量**（全文件搜索确认无 `environ` 引用 yaw_kp）。

**→ 早退分支每次都被命中 → `tau`/`ff` 从未被计算 → 打印 0。**

## 2. 更严重的后果：训练与评测的开关不一致

| 环节 | gyro-1 状态 | 证据 |
| --- | --- | --- |
| **训练** | **ON**（kp=60 cap=4） | 启动日志 `AS2W_GYRO_TRAIN_LOOP ON yaw_kp=60.0 ff_cap=4.00` |
| **我此前的 Isaac 评测** | **OFF** | 日志头 `########## armD1k ff=0.0`、每例 `ff_max=0.00` |

**→ 权重是在「有陀螺补偿」的条件下训练的，却在「无陀螺补偿」的条件下被评测。****→ 此前报告的 armD@1k = 7/11、armD@6.6k = 6/11、armC@5.6k = 6/11 全部是基线口径，不是 gyro-1 口径。**

**这是我自己的协议错误，且日志头早就打了 `ff=0.0`，我没有把它读成「陀螺是关的」。**

## 3. 修正后：显式 `--yaw-kp 60 --ff-cap 4`

### 遥测立刻恢复

```
每例: tau_max=13.50   ff_max=4.00   caps 从 9 累加到 581
```

- `tau_max = 13.50 Nm` = **力矩限幅的精确值**（90% 口径），说明限幅链路真的在起作用
- `ff_max = 4.00 Nm` = **`--ff-cap` 的精确值**，说明补偿确实被计算并**顶到了自身限幅**
- `caps` 累积到 **581 次**，说明补偿不是偶尔触发，而是**持续饱和**

**→ `tau/ff` 零读数问题解决：不是遥测缺陷，是开关没被送进去。**

## 5. 四条判断

**(a) 陀螺补偿确实有效，但只在「右转 0.10」上跨过了门槛。**`turn_right_0.10` 从 0.02 跳到 0.87 并 PASS（种子 7393），`arc_right` 0.76 → 0.87。**两侧都朝正确方向改善。**

**(b) 但补偿在左转 0.10 上把方向做反了。**`turn_left_0.10` 从 +0.35 掉到 **−0.03**（种子 7393），符号变负。`ff_max` 顶在 4.00 上限、`caps` 累计 581 次 → **补偿在左转方向过冲并反向**。

**(c) 左右仍然不对称。**同样 kp=60 cap=4：右转 0.10 → **0.87 PASS**，左转 0.10 → **−0.03 反向**。这与之前「左右不对称在两个仿真器上方向相反」一致 —— **补偿本身也在放大不对称**。

**(d) 力矩确实在饱和。**`tau_max` 每例都精确等于 13.50 Nm 限幅值、`caps` 持续累加 → **轮端在 90% 力矩上限处被夹住**。**这直接支持「实测轮速只有命令的 1/3」这一观察的第三种解释：不是接触打滑，而是力矩不够。**
